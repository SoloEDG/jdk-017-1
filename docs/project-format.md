# ORBIT 工程文件格式（.orbit）

版本：1（`orbit-project.json` 中 `version: 1`）

`.orbit` 是一个 **ZIP 容器**，把原始素材、取景、边缘设置和预览缩略图打包在一起，
可以在离线浏览器里重新打开并继续创作。运行时零依赖：ZIP 读写、SHA-256、
CRC-32 全部由应用自带实现，不加载任何外部脚本或字体。

## 容器布局

```
orbit-project.json      工程清单（UTF-8 JSON，见下）
assets/<sha256hex>.<ext>  素材负载，按内容寻址命名
preview.png             保存时的构图预览（512 × 512 PNG）
```

### 为什么用「不压缩（STORED）」的 ZIP

负载本身（PNG / JPEG / WebP）已经是压缩格式，再 DEFLATE 的收益接近零。
STORED 让中央目录里声明的体积**等于**真实体积，因此「超大解压体积」检查可以
在读取任何数据之前精确完成（防御解压炸弹），且实现简单、结果确定：
相同内容总是产出字节级相同的工程文件（条目时间戳固定为 1980-01-01）。

安全上限（打开时在中央目录阶段强制）：

| 限制 | 值 |
| --- | --- |
| 条目数 | ≤ 256 |
| 单条目解压后 | ≤ 256 MB |
| 全部条目解压后总量 | ≤ 512 MB |
| 条目路径 | 禁止 `..`、绝对路径、反斜杠、盘符 |

## 内容寻址与版本

- 每个素材以其字节的 **SHA-256** 命名（`assets/<hex>.<ext>`），清单通过
  `sha256:<hex>` 指纹引用。**重复引用同一份内容时只保存一份字节**。
- 打开时逐素材校验：条目存在 → 体积一致 → SHA-256 指纹一致 → 可解码 →
  尺寸与记录一致。任一失败都标记为可修复的问题，而不是整体崩溃。
- 版本记录在三处：清单 `version`（工程格式版本，当前 1）、素材
  `normalizeVersion`（规范化管线版本，当前 1 = 4096 × 2048 上限规则）、
  `app.version`。遇到未知版本直接拒绝打开并保留当前作品。

## 清单（orbit-project.json）

```jsonc
{
  "container": "orbit-project",
  "version": 1,
  "id": "8f3d…",                    // 工程 id，多次保存保持稳定
  "name": "未命名的星球",
  "createdAt": "2026-11-18T…",
  "modifiedAt": "2026-11-18T…",
  "app": { "name": "ORBIT", "version": "1.0.0" },
  "projection": { "mode": "tunnel", "zoom": 1.37, "yaw": 123, "pitch": -22, "roll": 45 },
  "edge": { "seam": 0.05, "feather": 0.12, "background": "#224466", "transparent": true },
  "activeAsset": "sha256:ab12…",    // 必须存在于 assets 列表
  "assets": [
    {
      "role": "source",
      "hash": "sha256:ab12…",
      "name": "山湖之间.jpg",
      "kind": "encoded",            // 或 "pixels"
      "mime": "image/jpeg",
      "width": 6000, "height": 3000, // encoded=原始尺寸；pixels=工作像素尺寸
      "bytes": 1024000,
      "normalizeVersion": 1          // 仅 encoded
    }
  ],
  "preview": { "hash": "sha256:cd34…", "width": 512, "height": 512 }
}
```

清单校验规则：结构/类型错误 → 拒绝（`bad-manifest`）；数值超界 → 按工作室
既有滑杆规则钳制而非拒绝；`version` 或 `normalizeVersion` 未知 → 拒绝
（`unsupported-version`）。

## 素材存储策略：原始编码照片 vs 规范化像素资源

| | `encoded` 原始编码照片 | `pixels` 规范化像素资源 |
| --- | --- | --- |
| 保存内容 | 原始文件字节（JPEG/PNG/WebP） | 工作分辨率（≤ 4096 × 2048）无损 PNG |
| 压缩体积 | **小**（示例工程 1.0 MB） | 大（同一工程 4.9 MB，照片内容约 3–6 倍） |
| 色彩复现 | 同一浏览器重解码结果确定；跨浏览器可能 ±1（IDCT/缩放实现差异） | **位精确**：重新打开后像素与保存时完全一致 |
| 再次编辑 | 保留原图全部信息，未来提高工作分辨率上限可受益 | 只剩工作分辨率，无法还原被裁掉的细节 |
| 依赖 | 依赖规范化管线版本（`normalizeVersion`） | 无 |

**取舍（默认「自动」策略）**：原始编码可嵌入（JPEG/PNG/WebP 且 ≤ 16 MB）时
用 `encoded`——体积优势明显，且同一离线浏览器内重解码是确定的；否则用
`pixels` 换取位精确复现。用户可在保存前手动覆盖。两种策略下重新导出的图片
都与保存时的构图、透明边缘一致（e2e 验证：导出字节 SHA-256 相同）。

## 打开流程：暂存区校验 → 一次切换

1. **结构**：ZIP 目录、条目数/体积上限、路径安全、CRC-32。
2. **清单**：JSON、容器标识、版本、引用完整性（`activeAsset` 必须存在）。
3. **资源**：逐素材指纹校验与解码、尺寸核对；预览缩略图损坏只降级为警告。
4. 全部通过后在暂存对象上构建完整工作区（素材像素 + 取景 + 边缘），
   用户确认后**一次性同步替换**当前工作区；任何一步失败都不触碰当前作品。
5. 缺图 / 指纹不符 / 条目损坏 → 列出问题，用户可**主动重新绑定**：
   选择本地图片后先验证可解码，指纹一致视为找回原内容；指纹不同则视为
   显式替换，记录进工程并在确认卡片上明示（旧指纹 → 新指纹），
   绝不静默换图。
